# 週末3CARDS データスキーマ仕様 v1.2（Phase 2）

このドキュメントは、スクレイパー出力・予想ロジック・UIの間の「契約」を定義する。
一度これを決めておけば、以降のタスク（取得項目の洗い出し・スクレイパー実装・結果集計）は
すべてこのスキーマを参照して進められる。

---

## 0. 全体像（ファイル構成）

3つのファイルで役割を分ける。

```
predictions.json   … 機械が生成（スクレイパー＋予想ロジック）。手で触らない。
comments.json      … 運用者が手で書く。キャラのセリフだけ。再生成の影響を受けない。
results.json       … レース後に機械が生成。的中判定・払戻。成績集計の元データ。
```

UIは predictions.json を主に読み、表示時に comments.json をレースID＋キャラIDで
突き合わせてセリフを合体させる。results.json は成績画面が読む。

## 1. predictions.json（機械生成・主データ）

### トップレベル

| フィールド | 型 | 説明 |
|---|---|---|
| `generated_at` | string(ISO8601) | 生成時刻。例 `2026-07-05T07:30:00+09:00` |
| `week_id` | string | 週識別子。ISO週。例 `2026-W27` |
| `myomi_threshold` | number | 鳳降臨の閾値。例 `80`。`myomi > myomi_threshold` で `legendary=true`。ここを変えれば降臨頻度をチューニングできる |
| `races` | array | レース配列（下記） |

### races[] の各レース

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | **内部主キー**。`YYYYMMDD-venue-RR`（R番号は**2桁ゼロ埋め**）。例 `20260705-kokura-01`、`20260705-kokura-11`。文字列ソートで正しい順になる。全ファイル突合の基準 |
| `source_refs` | object | 外部ソースのID。将来の複数ソース対応用（後述 §4） |
| `day` | string | `土` / `日` |
| `venue` | string | 開催場（日本語）。例 `小倉` |
| `race_no` | number | レース番号。例 `11` |
| `name` | string | レース名。例 `CBC賞` |
| `grade` | string | `g1`/`g2`/`g3`/`op`/`3win`/`2win`/`1win`/`mi` など。UIバッジ用 |
| `post_time` | string | 発走時刻 `HH:MM`。例 `15:35` |
| `course` | object | コース情報（下記） |
| `myomi` | number | 妙味メーター（0〜100）。旧 `distort` を改名。§3参照 |
| `myomi_parts` | object\|null | **（v1.2で追加・オプション）** 妙味の内訳 `{ "umami": number, "conf": number }`。umami=旨み度（0〜1）、conf=堅さ＝予測信頼度（0〜1）。`myomi ≒ 100 × umami × conf`。将来のUI2軸メーター化を無改修で可能にするために保持する（妙味メーター仕様 §5） |
| `legendary` | boolean | 鳳降臨フラグ。`myomi` が閾値超で true |
| `marks` | array | 予想印つき馬（下記） |
| `cards` | array | 予想師カード（下記） |

| 東京 | tokyo | | 中山 | nakayama |

### course（コース情報オブジェクト）

| フィールド | 型 | 説明 |
|---|---|---|
| `surface` | string | `芝` / `ダ` |
| `dist` | number | 距離(m)。例 `1200` |
| `heads` | number | 出走頭数。例 `18` |
| `note` | string\|null | 補足。例 `ハンデ`、なければ null |

### marks[]（印つき馬）

数値は生値で持ち、`%`や`円`などの整形はUI側の責務。

| フィールド | 型 | 説明 |
|---|---|---|
| `mk` | string | 印。`◎`/`○`/`▲`/`△`/`✕` |
| `hon` | boolean | 本命フラグ（◎を赤字表示する等）。省略時 false 扱い |
| `num` | number | 馬番 |
| `waku` | number | 枠番。枠色表示のルックアップ元 |
| `name` | string | 馬名 |
| `odds` | number\|null | 単勝オッズ。朝時点。取得できなければ null |
| `score` | number\|null | 合成スコア（予想ロジックの内部評価値）。妙味計算・検証に使用 |

### cards[]（予想師カード）

**枠番は持たない**。買い目は馬番のみで表現し、枠色はUIが marks からルックアップする。

| フィールド | 型 | 説明 |
|---|---|---|
| `char` | string | キャラID。`kei`/`tetsu`/`gen`/`otori` |
| `hit_pct` | number | 想定的中率(%)。数値のみ。例 `48` |
| `payout_range` | [number, number] | 払戻レンジ [下限, 上限]（円）。例 `[800, 1600]` |
| `total` | number | カード合計購入額(円)。通常500、鳳は1000。**不変条件：`total` = 全 `bets[].amt` の合計**（生成時に検証すること） |
| `bets` | array | 買い目（下記） |

### bets[]（買い目1点）

| フィールド | 型 | 説明 |
|---|---|---|
| `type` | string | 券種。`ワイド`/`馬連`/`3連複`。※単勝・複勝は使わない |
| `horses` | array[number] | 馬番の配列。ワイド/馬連は2頭、3連複は3頭。例 `[5,14]` |
| `amt` | number | 購入額(円)。例 `200` |

> `say`（セリフ）は predictions.json には**持たない**。comments.json 側（§2）。

## 2. comments.json（運用者が手書き・セリフのみ）

機械生成ファイルには一切触れず、セリフだけをここに書く。
再スクレイプしても消えない。手編集で壊しにくいよう構造は最小限。

```json
{
  "20260705-kokura-11": {
    "kei":   "◎5番はハンデ54kgで指数最上位。……美しい数字だ。",
    "tetsu": "▲9番の鞍上はね、小倉の芝短距離だと人が変わるんだよ。",
    "gen":   "17番！軽ハンデに小倉血統、笑いが止まらねぇ。"
  }
}
```

- キー1階層目 = レースID（predictions.json の `id` と一致）
- キー2階層目 = キャラID
- 値 = セリフ文字列
- 書いていないレース/キャラは、UI側で「（コメント準備中）」等のフォールバック表示

将来API直結に切り替える場合は、この comments.json を
LLMが自動生成して同じ形で吐くようにすれば、UIは無改修で済む。

## 3. myomi（妙味メーター）について

- 旧称 `distort`（歪み度）を `myomi` に改名。意味は「オッズと当モデル評価の乖離＝期待値の旨み」
- 0〜100の数値。閾値（サンプルでは80）超で `legendary=true`（鳳降臨）
- **計算式は Phase 2 で確定予定（未確定）**。方向性のみ：
  - モデル勝率とオッズ支持率の最大乖離
  - 期待値プラスの買い目の本数
  - レースの予測信頼度（頭数・実績データの揃い具合）
- 重要な緊張関係：「妙味が高い＝当たりやすい」ではない。妙味が高いレースは
  期待値は高いが的中率はむしろ下がりがち。この矛盾はキャラ（ケイ⇔源さん）が担う
- 将来案：1本のメーターを「旨み度」と「堅さ（信頼度）」の2軸に割る余地あり
  → **v1.2で `myomi_parts`（umami / conf）を追加済み**。JSONには常に出力し、UIは当面無視でよい。
    2軸メーターにしたくなった時点で、貯めた過去データも含めて無改修で移行できる
- `score`（marks内）と `odds` を残しているのは、後方検証
  （「妙味80超のレースは実際に回収率◯%だった」）を可能にするため

## 4. source_refs（複数データソース対応）

内部IDを主キーにし、外部ソースのIDは複数持てる形にする。
これにより netkeiba → JRA-VAN 等への切り替え・併用が、
予想ロジックを無改修で可能になる（取得と変換を分離する設計）。

```json
"source_refs": {
  "netkeiba": "202610020611",
  "jravan": null
}
```

- 当面 netkeiba のみ。他ソースは null
- 複数ソースから同一レースを取得した際の突合キーにもなる
- **設計原則**：ソースごとに「取得係（フェッチャー）」を作り、
  どの係も共通の内部フォーマットに変換してから予想ロジックへ渡す。
  ロジックは内部フォーマットしか知らないので、ソース追加＝フェッチャー追加だけで済む

```
netkeiba取得係 ─┐
JRA-VAN取得係 ─┼→ 共通内部フォーマット → 予想ロジック → predictions.json
(将来の何か) ──┘
```

この「共通内部フォーマット」の項目定義は、Phase 2 タスク2
（取得項目の洗い出し）で predictions.json と一緒に固める。

## 5. results.json（レース後・成績集計の元）

的中判定と払戻を記録。成績ダッシュボードが読む。詳細な券種別集計フィールドは
タスク7（成績集計の仕組み）で詰めるが、突合の骨格だけ先に定義しておく。

### トップレベル
| フィールド | 型 | 説明 |
|---|---|---|
| `updated_at` | string(ISO8601) | 最終更新時刻 |
| `results` | array | レース結果配列 |

### results[]
| フィールド | 型 | 説明 |
|---|---|---|
| `race_id` | string | predictions.json の `id` と一致 |
| `finish` | array[number] | 着順（馬番）。例 `[5,9,14]`（1着5番,2着9番…） |
| `dividends` | object | **公式配当表**（100円あたり、下記）。買い目に依存しない生データとして保持 |
| `cards` | array | カード別の的中結果（下記） |

### dividends（公式配当・100円あたり）

券種ごとに「的中組み合わせ → 配当」の配列。ワイドは3組が的中するため配列で持つ。

```json
"dividends": {
  "ワイド": [
    {"horses": [4, 9], "pay": 310},
    {"horses": [4, 1], "pay": 240},
    {"horses": [9, 1], "pay": 520}
  ],
  "馬連":   [ {"horses": [4, 9], "pay": 1840} ],
  "3連複": [ {"horses": [4, 9, 1], "pay": 2090} ]
}
```

> これを持つ目的：買い目生成ロジックを後から改良したとき、
> 「もし新ロジックで買っていたら収支はどうだったか」を**過去レース全部で再計算**できる。
> 重みチューニング（精度向上の本丸）に必須のデータ。

### 払戻の計算ルール（不変条件）

1. `bets[].payout` = 該当する `dividends` の `pay` × `amt` ÷ 100（外れは 0）
2. `cards[].payout` = そのカードの全 `bets[].payout` の合計
3. `cards[].spent` = 全 `bets[].amt` の合計 ＝ predictions側 `total` と一致
4. `cards[].hit` = 1点でも `bets[].hit=true` があれば true

集計スクリプトはこの4条件を検証し、崩れていたらエラーにすること
（スクレイプミス・配当の取り違えを早期検知できる）。

### results[].cards[]
| フィールド | 型 | 説明 |
|---|---|---|
| `char` | string | キャラID |
| `hit` | boolean | このカードが1点でも的中したか |
| `spent` | number | このカードの購入額（predictions側 `total` と一致） |
| `payout` | number | 払戻総額(円)。各買い目の payout 合計。外れは0 |
| `bets` | array | 各買い目の的中内訳（`{type, horses, amt, hit, payout}`） |

集計トップは「全予想師のカードを毎回すべて買った場合の累計収支」に一本化する方針。
合算の的中率のような曖昧な数値は出さない。マイナス収支も隠さず見せる。

## 6. 変更履歴（v7モックからの差分）

| 項目 | v7モック | v1スキーマ |
|---|---|---|
| 妙味の変数名 | `distort` | `myomi` |
| 的中率・払戻 | 整形済み文字列 `"48%"` `"800〜1,600円"` | 生値 `48` `[800,1600]` |
| 買い目の馬指定 | `[[枠,馬番],...]` | 馬番のみ `[5,14]` |
| セリフ | RACES内 `say` | comments.json に分離 |
| レースID | `r1`等の連番 | `YYYYMMDD-venue-R番号` |
| 外部ソースID | なし | `source_refs`（複数ソース対応） |
| オッズ・スコア | なし | marks内に `odds` `score`（検証用） |

## 6.5 v1 → v1.1 の変更点（ダブルチェックによる修正）

| 項目 | 修正内容 | 理由 |
|---|---|---|
| レースID | R番号を2桁ゼロ埋め（`-01`） | 文字列ソートで順番が狂うのを防ぐ |
| 開催場romaji | 10場の固定対応表を追加 | 表記ゆれでID突合が壊れるのを防ぐ |
| `myomi_threshold` | トップレベルに追加 | 鳳降臨閾値(80)がどこにも定義されていなかった |
| `total` | 不変条件（=Σamt）を明記 | 生成時検証でズレを検知 |
| `dividends` | results.json に公式配当表を追加 | ロジック改良時の過去レース再計算を可能に |
| 払戻計算ルール | 4つの不変条件を明文化 | v1サンプルに計算不整合があった（同じ買い目で払戻額が食い違う）。ルール未定義が原因 |

## 6.6 v1.1 → v1.2 の変更点

| 項目 | 修正内容 | 理由 |
|---|---|---|
| `myomi_parts` | races[] にオプションフィールドとして追加（`{umami, conf}`） | 引き継ぎ書v3 §2.1 で「持たせる」と決定したが、仕様書テキストに未反映のままだった（v3 §3-1・v6 §6 の未反映パッチ#1）。妙味メーター仕様 §5 の2軸分割を、貯めた過去データごと無改修で実現するために保持する |

> このv1.2が、コード各所（`scraper/common/constants.py`・`scraper/fetchers/b_shutuba.py`・
> `results/build_results.py`）が `データスキーマ仕様_v1_2.md` として参照していた版にあたる。
