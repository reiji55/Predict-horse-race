# 週末3CARDS 取得項目・共通内部フォーマット仕様 v1（Phase 2 タスク2）

この文書は「フェッチャー（取得係）が何をどこから取り、どんな形で吐くか」を定義する。
予想ロジックはこの**共通内部フォーマットだけ**を読む。ソース追加＝フェッチャー追加で済む、
というスキーマ仕様v1.1 §4の設計原則を具体化したもの。

```
netkeiba取得係 ──→ raw/{week_id}.json（共通内部フォーマット・本書§2）
                         │
                         ▼
                   予想ロジック（4ファクター合成 → 印 → 買い目 → 妙味）
                         │
                         ▼
                   predictions.json（スキーマ仕様v1.1 §1）
```

## 1. 取得項目の洗い出し

### 1.1 取得対象ページ（netkeiba）

| # | ページ | 1週あたり | 取得タイミング | 取れるもの |
|---|---|---|---|---|
| A | 開催日別レース一覧 | 2（土日各1） | 前日〜当日朝 | その日の全レースのrace_id、レース名、発走時刻、グレード → メインレースの特定 |
| B | 出馬表（shutuba） | 4〜6 | 当日朝 | レース基本情報、馬場状態、出走馬一覧（枠・馬番・馬名・性齢・斤量・騎手・厩舎・馬体重・単勝オッズ・人気） |
| C | 馬の戦績ページ（db.netkeiba.com/horse/） | 約70〜110（頭数×レース数） | 当日朝（キャッシュ可） | 過去走の全履歴（本書は直近5走を採用） |
| D | 騎手リーディング（場別） | 1〜2 | 当日朝 | 全騎手の当該場成績（着度数）を1ページでまとめて取得 |
| E | 調教師リーディング | 1 | 当日朝 | 全厩舎の成績（着度数） |
| F | レース結果・払戻ページ | 4〜6 | レース後 | 確定着順、公式配当表 → results.json用 |

**ページ数の概算**：1週あたり合計 **約90〜130ページ**。
1リクエスト3〜5秒間隔でも10分前後で完了し、GitHub Actionsの手動トリガー運用に収まる。

**マナー設計（規約グレー前提の自衛策）**：
- リクエスト間隔は最低3秒、ランダムゆらぎを入れる
- User-Agent を明示、リトライは1回まで
- 馬の戦績ページ（C）は**同一週内キャッシュ**（土曜に取った馬は日曜再取得しない）
- ページ構造変更で壊れる前提：パース失敗時は該当フィールドを null にして続行し、ログに残す（全体を止めない）

### 1.2 取得項目一覧（ファクター対応表）

用途欄の番号は引き継ぎ書の重視ファクター：①時計・指数 ②適性 ③騎手・厩舎 ④オッズ乖離（妙味）

| 項目 | 取得元 | 用途 | MVP |
|---|---|---|---|
| レース基本情報（場・R番号・名称・グレード・発走時刻・芝ダ・距離・頭数・ハンデ有無） | A, B | UI表示・全般 | ◎必須 |
| 当日の馬場状態（良/稍重/重/不良）・天候 | B | ①タイム補正・② | ◎必須 |
| 枠番・馬番・馬名・horse_id | B | 全ファクターのキー | ◎必須 |
| 性齢・斤量 | B | 補助（斤量は①の補正に将来使用） | ○取るだけ取る |
| 馬体重・増減 | B | 補助（当日情報） | ○取るだけ取る |
| 騎手名・jockey_id／調教師名・trainer_id | B | ③のキー | ◎必須 |
| 単勝オッズ（朝時点）・人気 | B | ④妙味メーターの主原料 | ◎必須 |
| 複勝オッズ（レンジ） | B | ワイド期待値の近似材料 | ○あれば取る |
| 式別オッズ（ワイド・馬連・3連複） | 別途オッズページ | 買い目の期待値を厳密計算 | ✕将来（下記注） |
| 過去走・直近5走（日付・場・芝ダ・距離・馬場・クラス・頭数・着順・走破タイム・上がり3F・着差・斤量・騎手） | C | ①②の主原料 | ◎必須 |
| 通過順位・ペース | C | 脚質分析 | ✕将来 |
| 血統（父・母父） | C | ②コース適性の血統面 | ✕将来（MVPは同条件実績で代用） |
| 騎手の当該場成績（着度数） | D | ③ | ◎必須 |
| 厩舎成績（着度数） | E | ③ | ◎必須 |
| 確定着順・公式配当表 | F | results.json | ◎必須 |

> **式別オッズを将来に回す理由**：ワイド・馬連・3連複のオッズは組み合わせ数が多く取得が重いうえ、
> 直前まで大きく動く。MVPでは**単勝オッズから式別的中確率を近似**（Harville式など）して
> 期待値・妙味を計算し、精度が欲しくなった段階で直前オッズ取得に切り替える。
> この差し替えが効くよう、共通内部フォーマットに `combo_odds` の置き場だけ予約してある（§2.4）。

## 2. 共通内部フォーマット（raw/{week_id}.json）

### 2.0 設計原則

1. **フェッチャーは「生の事実」だけを吐く**。率・指数・補正値の計算は一切しない（すべて予想ロジック側の責務）。成績は勝率でなく**着度数（生カウント）**で持つ。
2. **取れなかったら null**。フェッチャーは欠損で止まらない。欠損時の扱い（減点しない等）はロジック側で方針を決める。
3. **表記の正規化はフェッチャーの責務**。ソースごとの表記ゆれを、ここで定義する統一表記に変換してからロジックへ渡す。

### 2.1 正規化ルール

| 対象 | 統一表記 |
|---|---|
| レースID | スキーマ仕様v1.1と同一：`YYYYMMDD-venue-RR`（2桁ゼロ埋め、romaji対応表準拠） |
| 日付 | ISO8601（`2026-07-05`） |
| 芝ダ | `芝` / `ダ` |
| 馬場状態 | `良` / `稍重` / `重` / `不良`（netkeibaの「稍」「不」等は変換） |
| 走破タイム | **秒のnumber**（`1:09.8` → `69.8`） |
| 距離 | m のnumber |
| 着差 | 秒のnumber（タイム差換算できない表記＝大差等は null） |
| クラス | predictions.jsonのgrade表記に合わせる：`g1`/`g2`/`g3`/`op`/`3win`/`2win`/`1win`/`mi` |

### 2.2 トップレベル

| フィールド | 型 | 説明 |
|---|---|---|
| `fetched_at` | string(ISO8601) | 取得完了時刻 |
| `week_id` | string | `2026-W27`（predictions.jsonと同一） |
| `races` | array | 対象レース配列（土日のメイン4〜6） |

### 2.3 races[]

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | string | 内部主キー。predictions.jsonの `id` と**同一規則・同一値** |
| `source_refs` | object | `{"netkeiba": "202610020611", "jravan": null}` |
| `date` | string | `2026-07-05` |
| `day` | string | `土` / `日` |
| `venue` | string | 日本語。例 `小倉` |
| `race_no` | number | 例 `11` |
| `name` | string | 例 `CBC賞` |
| `grade` | string | 正規化表記（§2.1） |
| `post_time` | string | `HH:MM` |
| `course` | object | `{surface, dist, heads, note}`（predictions.jsonと同型） |
| `going` | string\|null | 当日朝の馬場状態 |
| `weather` | string\|null | `晴`/`曇`/`雨` など |
| `odds_updated_at` | string\|null | オッズ取得時点（「朝◯時のオッズ」を明示するため） |
| `entries` | array | 出走馬（§2.4） |

### 2.4 entries[]（出走馬1頭）

| フィールド | 型 | 説明 |
|---|---|---|
| `num` | number | 馬番 |
| `waku` | number | 枠番 |
| `name` | string | 馬名 |
| `horse_ref` | object | `{"netkeiba": "2021104567"}` 外部ID（source_refsと同思想） |
| `sex` | string | `牡`/`牝`/`セ` |
| `age` | number | 馬齢 |
| `impost` | number | 斤量(kg)。例 `54` |
| `body_weight` | object\|null | `{"value": 486, "diff": -4}`。発表前は null |
| `jockey` | object | `{"name": "◯◯", "ref": {"netkeiba": "01234"}}` |
| `trainer` | object | 同上 |
| `win_odds` | number\|null | 単勝オッズ（朝時点） |
| `place_odds` | [number, number]\|null | 複勝オッズ [下限, 上限] |
| `popularity` | number\|null | 人気順 |
| `combo_odds` | object\|null | **予約枠**。将来の式別オッズ用。MVPでは常に null |
| `past_runs` | array | 直近5走・新しい順（§2.5） |
| `jockey_stats` | object\|null | 騎手の当該場成績（§2.6） |
| `trainer_stats` | object\|null | 厩舎成績（§2.6） |

### 2.5 past_runs[]（過去走1件）

| フィールド | 型 | 説明 |
|---|---|---|
| `date` | string | `2026-05-10` |
| `venue` | string | 日本語場名（地方・海外はそのまま文字列） |
| `surface` | string | `芝`/`ダ` |
| `dist` | number | m |
| `going` | string\|null | 馬場状態 |
| `class` | string\|null | 正規化クラス表記 |
| `heads` | number\|null | 頭数 |
| `finish` | number\|null | 着順。中止・除外・取消は null（`note` に理由） |
| `time_sec` | number\|null | 走破タイム（秒） |
| `last3f` | number\|null | 上がり3F（秒） |
| `margin_sec` | number\|null | 勝ち馬とのタイム差（秒）。自身が1着なら 0 |
| `impost` | number\|null | 当時の斤量 |
| `jockey_name` | string\|null | 当時の騎手（今回と同じかの判定用） |
| `note` | string\|null | `中止`/`除外` 等の補足 |

> スピード指数（タスク3）の原料は `time_sec` + `going` + `venue` + `surface` + `dist`。
> 適性スコア（②）の原料は past_runs を「同場・同芝ダ・同距離帯・同馬場」でフィルタして作る。
> つまり**タスク3以降で必要なものはこの5走分に全部入っている**、というのがこの設計の狙い。

### 2.6 jockey_stats / trainer_stats（着度数・生カウント）

```json
"jockey_stats": {
  "scope": "venue",
  "venue": "小倉",
  "period": "2026",
  "starts": 42,
  "wins": 8,
  "seconds": 6,
  "thirds": 5
}
```

- 勝率・複勝率は持たない（ロジック側で `wins/starts` 等を計算）。分母が小さいときの扱い（例：騎乗10回未満は中立値）もロジック側で決められる
- `trainer_stats` は `scope: "overall"`（リーディングページの全体成績）で同構造
- リーディングページ（D・E）から**全騎手・全厩舎分を一括取得**し、出走馬に振り分ける方式。1頭ずつ騎手ページを叩かないのでページ数を大幅節約できる

## 4. 未確定・要確認（今回の提案込み）

| # | 論点 | 本書の提案 |
|---|---|---|
| 1 | 過去走は何走分か | **直近5走**（指数の安定性とスクレイプ量のバランス） |
| 2 | 式別オッズ（ワイド・馬連・3連複） | MVPは取得せず、**単勝オッズから近似**。`combo_odds` に予約枠のみ |
| 3 | 血統（父・母父） | **MVPスコープ外**。適性②は同条件の過去走実績で代用 |
| 4 | 騎手・厩舎成績の取り方 | 個別ページでなく**リーディングページ一括方式**（ページ数節約） |

この4点が確定したら、次はタスク3（スピード指数）またはタスク6（フェッチャー実装）へ。
本書の past_runs 定義はタスク3の入力仕様を兼ねている。
