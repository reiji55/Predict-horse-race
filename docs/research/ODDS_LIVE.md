# 全レースのオッズ記録（odds-live-v1）

- 書いた日：2026-10-31（2026-11-01・11-02 に ChatGPT のレビュー（PR #52）を受けて直した）
- 書いた人：Claude（ユーザーの指示「lab と共通で作り始めて」、2026-10-31 のチャット）
- 実装：`scraper/capture_odds_live.py`、`.github/workflows/run_odds_live.yml`、テスト `tests/test_capture_odds_live.py`
- 予想・正式成績・UI・snapshot・raw・scenario-frame/v1 には使わない（observe-only）。

## 何のための記録か

- **edge-loop**（[EDGE_LOOP.md](EDGE_LOOP.md) §8）：「市場が低く見ている組」を探すには、締め切り直前のオッズと確定オッズ、それに3連複のオッズ表が要る。今の記録はメインレースの、締め切りの1〜3時間前の値だけ（同 §6.2）。
- **lab**（`lab/research-design-v0` の `DATA_ACQUISITION_v0.md` §6）：全JRAレースの前向きのオッズ記録（判断時刻の発走30〜60分前と、確定オッズ）。2026-10-24 のオーナー判断 D1（取得元は netkeiba）・D3（JRA の平地全体）・D4（判断時刻は発走30〜60分前）に沿う。
- 二重に取らないよう、両方がこの記録を読む。

## 何を、いつ取るか

対象は、その日の JRA の平地の全レース（障害戦は取らない）。1レースにつき4回、4券種を取る。

| 回 | 時刻 | 意味 |
|---|---|---|
| `pre` | 発走30分前 | lab の判断時刻。取得元のオッズはおよそ1時間おきにしか新しくならないので、中身は発走の約65分前の値になることが多い（`source_time` を残す）。60分前に取っても同じ値になるので取らない。発走6分前を過ぎたら取らない |
| `close` | 発走3分前 | 締め切り直前の更新。予定の時刻より早くは取らない。発走1分前を過ぎたら始めない |
| `post1` | 発走25分後 | 発走後の観測。これだけでは確定オッズとみなさない |
| `post2` | 発走60分後 | 発走後の観測。`post1` と比べて、発走後の表が安定したかを `final_check` に書く |

券種は、単勝と複勝（API の type 1、1回の応答に両方入る）・3連複（7）・ワイド（5）・馬連（4）。締め切り直前に時間が足りなくなっても単勝と3連複が残るよう、この順に取る。

## 時刻の検証（券種ごと）

取得元が返すオッズの時刻（`official_datetime`）は時差の表記が無いので JST とみなし、`source_time_jst` に残す。取得を終えた時刻は `observed_at`。券種ごとに次の順で調べ、最初に当たったものを `status` にする。

| `status` | 条件 | 表（`odds`） |
|---|---|---|
| `after_post` | `pre`・`close` で、取得を終えたのが発走時刻以後 | 残さない |
| `source_time_unknown` | 取得元の時刻が無い・読めない | 残す（ok ではない） |
| `source_time_future` | 取得元の時刻が、取得を終えた時刻より60秒を超えて未来（取ったときに無いはずの時刻） | `pre`・`close` では残さない |
| `source_after_post` | `pre`・`close` で、取得元の時刻が発走時刻以後 | 残さない |
| `empty` | 表が空 | — |
| `ok` | 上のどれでもない | 残す |

- 60秒は、取得元と GitHub の実行環境の時計のずれとして許す幅。
- 下流（edge-loop・lab）は、`status` が `ok` の券種だけを使う。取得に失敗した券種は `fetch_failed`。
- 1回の観測の `status` は、全券種が ok なら `ok`、一部なら `partial`、どれも ok でなければ `failed`。取り逃した回は `missed`（理由 `started_too_late`）。

## 発走後の表の安定の確かめ方（`post2` の `final_check`）

券種ごとに、次をすべて満たしたら `verified: true` にする（`basis: stable_after_close`）。

- `post1` と `post2` の両方が `ok`。
- 両方の取得元の時刻が、締め切り（発走のおよそ2分前）より後。締め切り前の古い版のままなら `source_before_close` で確かめられない。
- 両方の表が同じ。違えば `changed_between_observations`。

`post1` が無い（取り逃した）なら `single_observation` で確かめられない。

- **`verified` の意味**：「締め切り後の同じ版を、発走後に2回見た」という安定の判定。取得元が確定と保証したことの証明ではない（2026-11-02 の ChatGPT の再レビュー）。
- **確定オッズとして使う条件**：`final_check.verified` が `true` の `post2` で、さらに使う側が払戻と照合して合っていること（3連複・馬連は当たり組のオッズ×100 が払戻と一致、ワイドは払戻が表の幅の中）。照合は、結果を取り込んだ後に使う側（edge-loop・lab）で行い、この記録には書かない。
- 表が変わったとき（`changed_between_observations`）に、3回目以降の観測で落ち着くのを確かめる形は、最初の開催日の結果を見てから考える。

**既存の記録での確認（2026-11-01）**：main の予想パイプラインが発走後に取り込んだ raw（10/31・11/1 のメインレース4レース、`raw/2026-W44.json` の `bc1fbc3`・`1efab5d`）は、4レースとも確定オッズだった。

- 4券種とも status は ok。取得元の時刻は、発走の7〜12分後（10/31 京都 15:51:55、東京 15:38:10、11/1 京都 15:27:05、東京 15:52:10）。
- 3連複・馬連の当たり組のオッズは、払戻と一致した。ワイドの払戻は、表の幅の中にあった。
- 10/31 は発走の約3時間半後に取ったが、取得元の時刻は発走の7〜8分後のままだった。

このとおりなら、`post1`（発走25分後）と `post2`（60分後）はどちらも確定後の同じ版を見るので、`verified` になる。全レースで同じかは、最初の開催日の `final_check` で確かめる。

## 置き場所と形式

- main ではなく **`odds-live` ブランチ**に置く。main の予想・成績集計の push とぶつからず、Pages の公開物にも入らない。ブランチは workflow の初回の実行で作る（main の履歴を持たない空のブランチ）。
- このリポジトリは公開なので、`odds-live` ブランチの中身（全レース・全券種のオッズ表）も誰でも見られる。公開の範囲はユーザーの判断による（PR #52 で確認中）。
- `{YYYYMMDD}/races/{HHMMSS}.json`：レース一覧の版。取った時刻ごとに1ファイルで、上書きしない。中身は対象レース（`race_key`・netkeiba のレースID・場・R・発走時刻・芝ダ・距離・頭数・クラス）と、一覧の検査の結果。レース名などの文字列は残さない。
- `{YYYYMMDD}/{race_key}/{pre|close|post1|post2}.json.gz`：1観測1ファイル。上書きしない。gzip の時刻は 0 にしてあり、同じ中身なら同じバイト列になる。
- `{YYYYMMDD}/runs/{run_id}-{attempt}.json`：workflow の実行ごとの記録（起動のされ方、始まった時刻・終わった時刻、終わり方）。
- 取得元のレスポンス本文・URL・リクエスト固有の値は残さない（数値と時刻だけ）。

## レース一覧の取り直し

- 最新の版が1時間より古いと、取り直して新しい版として残す。次の予定までの待ちが長いときも、取り直しの時刻には起きて取り直す。
- **一覧の検査**（障害戦も含めて数える）。次のどれかに当たれば `partial_unverified` とし、10分おきに取り直す。当たったものは `check.problems` に残す。

  | `problems` | 意味 |
  |---|---|
  | `no_races` | レースが1つも無い |
  | `venue_without_races` | 場の見出しはあるのに、その場のレースが1つも読めなかった（部分的にしか読めなかった疑い） |
  | `gap_in_race_numbers` | 場ごとのレース番号が1から抜けなく並んでいない |
  | `fewer_than_12_races` | 12レースに足りない場がある（後半が欠けた疑い。JRA は1場1日12レース） |
  | `fewer_than_2_venues` | 場が2つ未満（場がまるごと欠けた疑い。開催は普段2〜3場） |

  本当に少ない日（1場だけの日など）も `partial_unverified` になるが、取り直しが増えるだけで、取る予定は変わらない。
- 場の見出しは、レース一覧と同じ応答から読む（`scraper/fetchers/a_race_list.py` の `fetch_race_list_with_venues`。予想パイプラインが使う `fetch_race_list` は変えていない）。
- **欠けの疑いが残ったまま予定を取り終えたとき**は、すぐには終えない。最後の一覧をその日の最後の予定より前に取っていたら、もう一度取り直してから終える。後から見つかったレースは、発走前の回は取り逃し（`missed`）になるが、発走後の2回は取る。取り直しに失敗したら、そのまま終える。
- 予定は全部の版の和（一度でも載ったレースは消さない）。発走時刻は、そのレースが載っている最新の版のものを使う。
- 取り直しに失敗したら前の版を使う。一度も取れていなければ何も書かずに失敗にし、次の実行で取り直す（空の一覧を残すと、その日の後の実行が全部空振りするため）。

## 動かし方

- 定時実行は数時間遅れることがある（11/1 は 13:00 の予想パイプラインの枠が 15:56 まで動かなかった）。そこで、土日に8つの枠を置いている。
  - 朝の5つ（06:40・08:10・09:40・11:10・12:40 JST）：1日を始める。
  - 午後の3つ（14:10・15:40・17:10 JST）：自己起動が消えたときに、1日をつなぎ直す（下）。17:10 は最終レースの発走60分後の観測まで。
- **対象日**：定時実行は、実行した時刻ではなく枠の日付（JST）を対象にする（`--scheduled-date`）。遅れて日をまたいでも、翌日を取りに行かない。手動の起動は `date` を指定する（空なら JST の今日）。
- 1回の実行は「次の予定まで待ち、その時刻に来ている予定を取る」を繰り返し、そのたびに `odds-live` にコミットする。
- 取る順は `close` → `pre` → `post1`・`post2`。`close` が2分以内に来るときは、他の取得を始めずに `close` を待つ。
- 実行は最大約5時間半で区切り、予定が残っていれば次の実行を自分で起動して1日をつなぐ。
- 同時には1つしか走らない（concurrency）。GitHub は待っている実行を1つしか残さず、新しく来た実行が、前に待っていた実行と入れ替わる。どの実行も「その日の、まだ取っていない予定」を続けるだけなので、入れ替わっても1日はつながる。
  - 自己起動した実行が、待っている間に別の実行と入れ替わって消えることがある。入れ替わった実行も同じ日の続きを取るので、ふつうは途切れない。途切れるのは、待っていた実行が別の日付の手動起動と入れ替わったときと、最後の実行が予定を残したまま消えたとき。後者は午後の枠がつなぎ直す。
  - 入れ替わって消えた実行は `runs/` に残らない（GitHub の実行一覧で cancelled として見える）。
- **最初の開催日の確かめ方**（Claude が開催日の流れで行う）：
  1. `runs/` で、実行の始まり・終わり・終わり方（3＝その日の予定が終わった、4＝時間切れで次を起動）がつながっているか。
  2. 回ごとの `missed`（`started_too_late`）の数。朝の遅れで出る `pre`・`close` 以外に、昼以降にまとまって出ていれば、つなぎが途切れている。
  3. 一覧の版の `check.problems`。欠けの疑いがあれば、場の数とレースの数を公式の開催と照らす。
  4. `post2` の `final_check` と、払戻との照合。
- 祝日の開催は、`date` を指定して手動で起動する。
- **予想パイプラインの起動と確認（2026-11-11 から）**：odds-live は実行の初めに、別のワークフロー `run_pipeline_kick.yml`（`scripts/kick_pipeline.py`）を起動する（待たない）。
  - 9:50・12:50（JST）に予想パイプラインを、対象日と週を指定して `workflow_dispatch` で起動し、**対象の全レースに発走前の凍結版ができたかを生成物で確かめる**。
    - 対象は、その日の odds-live のレース一覧（最新の版で、一覧の検査が ok のもの）から、予想パイプラインと同じ規則（11R・JRA の場・1日の上限）で選んだレース。一覧が無い・検査が ok でなければ「対象が分からない」とし、できたとはみなさない（起動はする）。
    - できたとみなすのは、対象のどのレースにも、main の履歴に `pre_race: true` で、`frozen_at` がその時刻の20分前から 14:45 までの間にあり、発走より前の版があるとき。1レースでも足りなければできていない。14:45 より後の凍結（11/7 京都の 15:42 のような版）は数えない。実行が作られた・成功しただけでは、できたとみなさない。
  - できていなければ：予想パイプラインの実行が待ち・実行中なら、重ねずに待つ。無ければ起動する（この監視の実行1回の中で、1時刻3回まで）。その時刻の分は次の時刻まで（最後は 14:45 まで）見て、そろわなければ足りないレースを残して警告を出し、失敗（赤）にする。
  - 予想パイプライン（`run_pipeline.yml`）は concurrency `pipeline` で1つずつ動き（実行中は取り消さない）、1回は30分で打ち切る。定時・手動・この起動が重なっても、main で生成物が競合しない。
  - odds-live とは別の concurrency なので、こちらの待ちが odds-live の次の実行を止めない。odds-live が動かない日に備えて、土日 06:50 JST の定時も置く。
  - `workflow_dispatch` の受付は、実行の時刻を保証しない。凍結版ができたかは、毎回この確認で見る。

## 取得の量

- 1レースにつき 4回 × 4券種 = 16回。1日24〜36レースで、およそ380〜580回になる。これに、レース一覧の取り直し（1回に2件。欠けの疑いが無ければ1時間に1回、あれば10分に1回）が加わる。
- 間隔は `scraper/common/http.py` のマナー（3秒以上とゆらぎ、UA を偽らない、リトライ1回）に従う。並列にはしない。

## 分かっている限界

- 定時実行の遅れが大きい日は、朝のレースの `pre`・`close` を取り逃す（`post1`・`post2` は後からでも取る）。開催日の昼の流れで手動起動しておけば、午後のレースは取れる。
- 取得元のオッズの更新が「およそ1時間おき」という観測は、メインレースの記録から得たもの（EDGE_LOOP.md §6.2）。他のレースでも同じかは、この記録の `source_time` で確かめる。
- 取得元が発走後に確定オッズを返すことは、メインレースの4レースでしか確かめていない（上の「既存の記録での確認」）。全レースで同じかは `final_check` で分かる。
- 発走の直前に同じ時刻のレースが重なると、後に回したレースの `close` を取り逃すことがある（その場合は `missed` が残る）。
- 一覧の検査は目安で、公式の開催予定とは照らしていない。場がまるごと欠けて見出しも無く、残りの場が2つ以上で12レースそろっていれば、欠けに気づかない。
- テストは時計と取得を差し替えたもので、実際の取得元・GitHub Actions の長時間の実行・自己起動のつなぎは、最初の開催日に確かめる。
