# 全レースのオッズ記録（odds-live-v1）

- 書いた日：2026-10-31
- 書いた人：Claude（ユーザーの指示「lab と共通で作り始めて」、2026-10-31 のチャット）
- 実装：`scraper/capture_odds_live.py`、`.github/workflows/run_odds_live.yml`、テスト `tests/test_capture_odds_live.py`
- 予想・正式成績・UI・snapshot・raw には使わない（observe-only）。

## 何のための記録か

- **edge-loop**（`docs/research/EDGE_LOOP.md` §8、PR #51）：「市場が低く見ている組」を探すには、締め切り直前のオッズと確定オッズ、それに3連複のオッズ表が要る。今の記録はメインレースの、締め切りの1〜3時間前の値だけ（同 §6.2）。
- **lab**（`lab/research-design-v0` の `DATA_ACQUISITION_v0.md` §6）：全JRAレースの前向きのオッズ記録（判断時刻の発走30〜60分前と、確定オッズ）。2026-10-24 のオーナー判断 D1（取得元は netkeiba）・D3（JRA の平地全体）・D4（判断時刻は発走30〜60分前）に沿う。
- 二重に取らないよう、両方がこの記録を読む。

## 何を、いつ取るか

対象は、その日の JRA の平地の全レース（障害戦は取らない）。1レースにつき3回、4券種を取る。

| 回 | 時刻 | 意味 |
|---|---|---|
| `pre` | 発走30分前 | lab の判断時刻。取得元のオッズはおよそ1時間おきにしか新しくならないので、中身は発走の約65分前の値になることが多い（`source_time` を残す）。60分前に取っても同じ値になるので取らない |
| `close` | 発走3分前 | 締め切り直前の更新。券種ごとに、取得を終えた時刻が発走時刻を過ぎていたら残さない（`after_post`） |
| `final` | 発走25分後 | 確定オッズ。発走後の値なので、発走前の入力には使わない。取得元が発走後も確定オッズを返すかは、最初の実行で確かめる |

券種は、単勝と複勝（API の type 1、1回の応答に両方入る）・3連複（7）・ワイド（5）・馬連（4）。締め切り直前に時間が足りなくなっても単勝と3連複が残るよう、この順に取る。

## 置き場所と形式

- main ではなく **`odds-live` ブランチ**に置く。main の予想・成績集計の push とぶつからず、Pages の公開物にも入らない。ブランチは workflow の初回の実行で作る（main の履歴を持たない空のブランチ）。
- `{YYYYMMDD}/races.json`：その日の対象レース（`race_key`・netkeiba のレースID・場・R・発走時刻・芝ダ・距離・頭数・クラス）。レース名などの文字列は残さない。
- `{YYYYMMDD}/{race_key}/{pre|close|final}.json.gz`：1観測1ファイル。上書きしない。gzip の時刻は 0 にしてあり、同じ中身なら同じバイト列になる。
- 各ファイルの `markets` に、券種ごとの `status`・`observed_at`（取得を終えた時刻）・`source_time`（取得元が返したオッズの時刻）・`rows`・`odds` を入れる。単勝は `popularity` も。複勝とワイドは `[下限, 上限]`。
- 取り逃した回も、`status: missed` と理由（`started_too_late`）を書いたファイルを残す。
- 取得元のレスポンス本文・URL・リクエスト固有の値は残さない（数値と時刻だけ）。

## 動かし方

- 定時実行は数時間遅れることがある。そこで、土日の朝に5つの枠を置いている（06:40・08:10・09:40・11:10・12:40 JST）。
- 1回の実行は「次の予定まで待ち、その時刻に来ている予定を全部取る」を繰り返し、そのたびに `odds-live` にコミットする。
- 実行は最大約5時間半で区切り、予定が残っていれば次の実行を自分で起動して1日をつなぐ。同時には1つしか走らない。後から来た枠は、取り終えた予定を取り直さないので、すぐ終わる。
- 祝日の開催は、`date` を指定して手動で起動する。
- レース一覧を取れなかったときは何も書かずに失敗にし、次の実行で取り直す。

## 取得の量

- 1レースにつき 3回 × 4券種 = 12回。1日24〜36レースで、およそ290〜430回に、レース一覧の2回が加わる。
- 間隔は `scraper/common/http.py` のマナー（3秒以上とゆらぎ、UA を偽らない、リトライ1回）に従う。並列にはしない。

## 分かっている限界

- 定時実行の遅れが大きい日は、朝のレースの `pre`・`close` を取り逃す（`final` は後からでも取る）。開催日の昼の流れで手動起動しておけば、午後のレースは取れる。
- 取得元のオッズの更新が「およそ1時間おき」という観測は、メインレースの記録から得たもの（EDGE_LOOP.md §6.2）。他のレースでも同じかは、この記録の `source_time` で確かめる。
- 発走の直前に同じ時刻のレースが重なると、後に回したレースの `close` を取り逃すことがある（その場合は `missed` が残る）。
