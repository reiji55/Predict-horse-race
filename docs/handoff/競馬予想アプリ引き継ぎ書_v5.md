## 2. C（馬戦績）で確定した実装内容と技術的発見

実サンプル：ヴァルキリーバース（`db.netkeiba.com/horse/2022104764`、全6走）で検証。

### 2.1 テーブル構造

- 戦績テーブルは `table.db_h_race_results`（thead/tbody あり）。tbody 内の各 tr が1走。
- 列インデックス（0始まり・33列）：
  `0=日付 1=開催 4=レース名 6=頭数 11=着順 12=騎手 13=斤量 14=距離(surface+dist) 16=馬場 18=タイム 19=着差 27=上り3F`
- 実装は `parse_horse_history_html(html, n_runs)`（オフライン解析用に公開）＋
  `fetch_horse_history(horse_ref, n_runs)`（実取得）＋
  `fetch_horse_history_cached(horse_ref, cache, n_runs)`（週内キャッシュ版）。

### 2.2 パースで効いた注意点（実装済み）

| 項目 | 内容 |
|---|---|
| 開催列 | `"3東京6"`（回+場+開催日数）。先頭・末尾の数字を除いた中央部だけ場名抽出。地方・海外場もこの方式で文字列そのまま取れる（§2.5設計どおり） |
| 馬場状態 | 単一文字略記（`稍`/`不`）で来る。既存 `constants.GOING_NORMALIZE` がカバー |
| クラス判定 | レース名列にクラス情報が同居。3パターン混在：括弧内グレード`(GIII)`、括弧内条件`(1勝クラス)`、括弧なし`3歳未勝利`。`GRADE_TAG_MAP`→`CONDITION_GRADE_MAP` の順で判定 |
| 走破タイム | `"1:48.0"`(分:秒)と`"58.2"`(秒のみ)の両対応。秒に正規化 |
| 着差（1着馬） | netkeibaの生値は表記が一定しない（1着でも 0.0 や負値）。**finish==1 のとき margin_sec=0 に上書き**（共通内部フォーマット仕様§2.5「自身が1着なら0」に準拠） |
| 着差（換算不能） | `"大差"`等は margin_sec=null（仕様§2.1） |
| 着順（非数字） | 中止・除外・取消・失格等は finish=None、生テキストを note に格納 |
| 障害走 | surfaceに`障`も出現しうる。フェッチャーは判断せず記録（§2.0原則1）。スピード指数§2のusable判定で自然に除外される |

### 2.3 共通化した定数（v5でリファクタ）

`b_shutuba.py` にあったクラス判定マップを `scraper/common/constants.py` に移動し、C と共有：
- `CONDITION_GRADE_MAP`（条件文字列→クラスキー。**新馬→mi を新規追加**、§3参照）
- `GRADE_TAG_MAP`（括弧内グレード `GI/GII/GIII/L` → クラスキー。**L（Listed）は op に丸め**）

## 3. ⚠ 実装中に生じた「要確認」の設計判断（2点・認識合わせ）

C実装で仕様書に明記のない判断を2つ入れた。妥当と考えるが、明示決定ではないので記録する。

| # | 判断 | 内容と理由 |
|---|---|---|
| 1 | **新馬戦のクラス区分** | class_offset（スピード指数§1.3）に「新馬」専用キーが無いため、**未勝利(`mi`)と同一区分に丸めた**。新馬戦は「同条件実績が皆無」という点で未勝利ともニュアンスが違うが、v1では割り切り。将来、新馬専用の class_offset を足す余地あり |
| 2 | **週内キャッシュの永続化範囲** | 追加した `fetch_horse_history_cached()` は**プロセス内キャッシュ**（1回の build_week 実行内）。土日を**別々のActions実行**で回す運用だと、実行をまたいだキャッシュにならず日曜に再取得が走る。運用が「週1回一括」か「土日別起動」かで対応要否が変わる → **A（レース一覧）実装時に運用形態を確認したい** |

## 4. 次にやること：D・E（リーディング）／A（レース一覧）

取得項目仕様 §1.1（表D・E・A行）・§2.6（stats型）が仕様。

- **D 騎手リーディング（場別）**：`fetch_jockey_leading(venue_jp, period)` → `{jockey_ref: jockey_stats}`。
  jockey_stats は §2.6（scope="venue", venue, period, starts, wins, seconds, thirds）。着度数の生カウントで保持。
- **E 調教師リーディング**：`fetch_trainer_leading(period)` → `{trainer_ref: trainer_stats}`（scope="overall"）。
- **A レース一覧**：`fetch_race_list(date_str)` → メインレース特定。
  **【要確認】メインレースの絞り込みルール**（全レース対象か、指定グレード以上か等）が未確定（a_race_list.py のTODO）。
- 紐付けキー：出走馬の jockey_ref / trainer_ref（B出馬表で取得済み）とリーディング表を突合。

いずれも v4/v5 と同じ流れ（**HTMLサンプル入手 → 構造解析 → 実装 → 実サンプルで検証**）。
HTMLサンプルは webarchive（Safari）でも代用可（v5でCはこの方式で成功。plistlib でHTML抽出できる）。

## 5. 進め方のルール（v3から継続・維持）

- **モデル**：実装フェーズなので Sonnet 継続。設計・仕様整合チェックは Opus、重いエージェント実装は Fable。
- **チャット分割**：コンテキストが膨らんだら引き継ぎ書を書いて新規チャットへ（この運用の継続）。
- **切替アナウンス**：モデル切替・チャット分割の適切なタイミングはアシスタント側から知らせる。
- **対話スタイル**：運用者は要望・ニュアンス主体。認識のズレ・データ不足・誤認識は都度指摘。「なんとなく」で進めない。
- **大きい生データ**（base64・HTML等）はチャット直貼りで停止することがあるのでファイル添付を使う。
- ギャンブル/ハウスエッジは理解済み。射幸性を煽らず正直な成績表示を重視。

### 7.4 チューニング（データが貯まってからが本番）

これは「データ補完」ではなく**運用で貯めた results.json を使った重み調整**。精度向上の本丸。

- スピード指数の各係数（k_impost, going_adj, class_offset, scale_mode の distance/flat 比較）
- 合成スコアの重み（①0.45/②0.30/③0.25）、③内訳（騎手0.6/厩舎0.4）、縮小推定 m
- 妙味の T（温度）・各cap・weight、myomi_threshold（鳳降臨頻度）
- キャラ別 λ（ケイ0.15/哲0.40/源0.75/鳳0.60）、券種テンプレの点数配分
- **後方検証の目玉**：「myomi 80超のレースは実際に回収率◯%だったか」で運用者の原点仮説
  （参加者の少ないレースは歪む）そのものを検証（妙味§6）

> このために **results.json に dividends（公式配当）と marks[].score / odds を残す設計**にしてある。
> raw/{week_id}.json もコミット対象にした（v2修正）ので、過去週の生データから丸ごと再計算できる。
