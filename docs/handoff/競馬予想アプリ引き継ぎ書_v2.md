## 2. タスク2〜4で確定した設計判断（重要な決定のみ）

### タスク2（取得・共通内部フォーマット）— 4点すべて確定
- 過去走は **直近5走**
- 式別オッズ（ワイド/馬連/3連複）は **MVP非取得**。単勝オッズから近似（Harville等）。`combo_odds` は予約枠のみ
- **血統はMVPスコープ外**。適性は同条件の過去走実績で代用
- 騎手・厩舎成績は個別ページでなく **リーディングページ一括取得**（着度数＝生カウントで保持）
- フェッチャーは「生の事実だけをnull許容で吐く」。率・指数の計算はロジック側

### タスク3（スピード指数）— §7の5点すべて確定
- 指数 **100 = 各コースのOPクラス勝ち馬水準**
- **基準タイム表**は初期構築スクリプト（1回きり）で自動生成→ config/base_times.json（タスク6のサブタスク）
- 距離換算 **あり**（短距離の1秒を重く）。flat と切替可能にして後方検証
- **斤量補正あり**（k=0.10秒/kg・2000m基準／初期値）
- 3段補正（基準タイム・馬場・斤量）。**係数は全て初期値、後方検証でチューニングが本丸**
- ダートは湿ると速くなるので馬場補正の符号が芝と逆（実装時の注意点）

### タスク4（妙味メーター）— 下書き完了、方針
- 妙味 = 3成分：**A旨みの深さ（最大EVエッジ）× B旨みの広がり（過小評価の総量）× C信頼度**
- スコア→勝率 p は softmax（温度T）。**この変換はタスク5と共有する部品**
- オッズの控除率(20%)を数式に織り込み、「+EVの敷居はハウスエッジぶん高い」を正直に表現
- 「妙味高い≠当たりやすい」は追加ペナルティ不要で式に内在（人気薄を狙うほど妙味↑・的中率↓）
- **旧構想からの変更**：材料②「+EV買い目の本数」→「勝率空間の過小評価の広がり(B)」に置換（combo_odds非依存にするため）

## 3. 次チャットの冒頭で相談したい未確定2点（タスク4 §7残り）

タスク5に入る前にここを詰める。

1. **信頼度Cに「頭数」を入れるか**
   v1案は入れず（データ被覆率のみ）。理由は「小頭数＝高信頼」とも「大頭数＝旨み機会増」とも
   言え方向が両義的なため。運用者の原点仮説（参加者が少ないレースは歪む）とも絡むので相談したい。
2. **`myomi_parts`（旨み度・堅さの内訳）を predictions.json に持たせるか**
   v1案は「持たせる」推奨（将来の2軸メーター化に無改修で対応）。UIは当面無視でよい。

## 4. タスク5（買い目生成）でやること

確定済みの部品：合成スコア→印→リスク別カードへの変換ルール、鳳の1,000円配分。
必要な入力（既に定義済み）：各馬の合成スコア、印、モデル勝率p（タスク4の変換）、単勝オッズ。

- **合成スコアの中身（4ファクター合成）自体もタスク5で確定する**
  （①スピード指数=タスク3済 ②適性 ③騎手厩舎 ④オッズ乖離 の重み付き合成）
- キャラ別リスク許容度（ケイ=低/哲=中/源=高/鳳=確変）→ 印の組み合わせ→買い目の機械生成ルール
- 券種：ワイド・馬連・3連複のミックス。1カード500円（鳳1000円）、`total`=Σamt の不変条件を守る
- 式別オッズ非取得なので、各買い目の期待値は単勝オッズからの近似で評価

## 5. 進め方のルール（オペレーション）★新チャットでも維持してほしい

運用者の明示的な希望。以下を守って進めること。

### 5.1 モデルの棲み分け（トークン消費削減）
- **設計・理論構築・仕様の整合性チェック（間違うと全部やり直しになる部分）→ Opus**（または重いエージェント実装時は Fable）
- **確定した仕様書どおりに書くだけのコード実装 → Sonnet**（新規チャットに仕様書だけ渡す）
- Fable はクレジット消費が大きいので、機能の根幹の設計判断に温存。単純なコード書きには使わない
- 注：Fable は一部トピックで自動的に Opus 4.8 に振り分けられる安全機構がある

### 5.2 チャットが重くなったら分割
- コンテキストが膨らんだら、**引き継ぎ書を書いて新規チャットへ移る**（この運用の継続）
- 重い処理（画像base64の反復など）はコンテキストを膨らませるので区切りで引き継ぐ

### 5.3 切り替えのアナウンス
- 「今はこの作業だから Opus のままでよい／ここは Sonnet に渡すべき／Fable の出番」など、
  **モデル切替やチャット分割の適切なタイミングが来たらアシスタント側から知らせる**
- 現状の判断：設計フェーズ（タスク5まで）は Opus 継続でよい。実装フェーズ（タスク6以降）で Sonnet へ

### 5.4 対話スタイル
- 運用者は要望・ニュアンス主体で話す。厳密な仕様は対話で詰める
- **認識のズレ・データ不足・誤認識に基づく発言は都度指摘する**（本人の明示的要望）
- 理解が追いつかない時は噛み砕いて説明する。「なんとなく」で先に進めない
- ギャンブル/ハウスエッジは理解済み。射幸性を煽らず正直な成績表示を重視

## 7. アプリ概要（リマインド）

- **名称（仮）**：週末3CARDS。土日メインレース対象、リスク度別3枚カード（+確変4枚目=鳳）で買い目と一言分析
- **予想師4人**：🧑‍🎓ケイ(低/堅実) 👨‍👧哲さん(中/バランス) 👴源さん(高/大穴) 🎩鳳(確変/降臨時のみ)
- **プラットフォーム**：PWA（GitHub Pages）、月額0円構成（Actions手動トリガー）
- **エンジン**：統計ロジック中心＋LLMコメント（当面は手動でcomments.jsonに流し込み）
- **成績表示**：全カード購入時の累計収支に一本化、マイナスも隠さない（正直さ＝信頼性）
