## 2. D・E で分かったこと（実サンプル解析）

### 2.1 APIの特定

リーディングページも A・B2 と同じ「静的HTMLは空、AJAXが後から描画」パターン。
ページ内のインラインJSに呼び出しパラメータがそのまま書かれており、
`org_dbapi.action.js` の `getLeadingData()` が下記を投げていた：

```
GET https://db.sp.netkeiba.com/
    ?pid=api_get_leading&input=UTF-8&output=json
    &limit=20&category={jockey|trainer}&page=1&show=leading_detail
    &bel=&year=2026&sort_key=win
```

- **D と E は `category` が違うだけの同一API** → `scraper/common/leading_api.py` に共通化
- レスポンスは **HTML断片をJSON文字列で包んだもの**（`output=json` でも生JSONではない）
- v7 §2.2 で見つけていた `ajax_leading_box.html` は別系統（サイドバーの要約box）。本命はこちら

### 2.2 ★ jockey_ref の桁合わせ（v7 §2.5 の要確認事項）→ 解消

レスポンスの騎手リンクは `db.sp.netkeiba.com/jockey/01174/` の形で、**5桁ゼロ埋め**。
B出馬表で取得している `jockey_ref` と同形式であることを確認した（Ｃ.ルメール＝05339）。
振り分けが壊れる懸念は無くなった。

### 2.3 ⚠ 着度数が載っていない（OPEN_QUESTIONS C-7）

レスポンスに入るのは **勝利数・勝率・連対率** だけで、取得項目仕様§2.6 が求める着度数は無い。
そこで率から逆算している：

```
starts  = wins / 勝率
seconds = starts × 連対率 − wins
thirds  = starts × 複勝率 − wins − seconds   ← 複勝率が載っていれば
```

率は小数第1位までなので starts に丸め誤差が乗るが、分母が数百なので相対誤差1%未満。
③人的スコアは縮小推定を通すため実用上問題ない。

**ただし複勝率は `sort_key=win` のレスポンスに載らない**ため、現状 `thirds=None`。
③は買い目生成仕様§1.5 が定める複勝率ではなく **連対率** で評価している
（全騎手が同じ指標で揃うので、レース内z標準化の相対評価としては同等に機能する）。
→ **`sort_key=avt`（複勝率順）のレスポンスを1件もらえれば解消できる**。

### 2.4 ⚠ limit が効かない（C-8）

`limit=100` を指定しても20件しか返らない（サーバー側で固定）。
既定で5ページ＝**上位100人**まで取得し、表に載らない騎手は `jockey_stats=None`（③欠損）。
メインレースに乗るのは上位騎手が中心という前提での割り切り。

### 2.5 場別リーディングは存在しない（v8 から継続・確定）

PC版 `?pid=jockey_leading` は実体が無く、sp版の絞り込みは 全国/関東/関西＝**所属**のみ。
取得項目仕様を **v1.1** に改訂して騎手も `scope="overall"` にした（`venue` フィールドは廃止）。

## 3. F で分かったこと（実サンプル解析）

**このページは素のHTMLに中身が入っている**（AJAXではない）。2026-09-13 中山1R で検証。

- **着順**：`table#All_Result_Table` の 0=着順 / 2=馬番。中止・除外の行は除外する
- **払戻**：`table.Payout_Detail_Table` の行class で券種を判別
  （`Wide` / `Umaren` / `Fuku3` が本アプリの3券種。単勝・複勝・枠連・馬単・3連単も同じ構造）
  - 組み合わせは **`<ul>` 1つ＝1組**（空の `<li>` は桁合わせの埋め草）
  - 配当は `td.Payout` のテキストを **`<br>` で分割**して組の順に対応させる
  - この構造なので、**ワイドの3組も同着の複数配当もそのまま正しく取れる**
- Fの戻り値は `results.build_results.build_results()` にそのまま渡せる形にしてある

### 【発見】1日分の払戻をまとめて取れるページ

`race.netkeiba.com/top/payback_list.html` は**その日の全レースの払戻表**を1ページに持つ
（実サンプルでは12レース分＋各レースの race_id リンク）。ただし**着順が載っていない**ので
results.json には使えない。過去分を一括で埋めたくなったときの選択肢として記録しておく。

## 4. 基準タイム表の構築スクリプト（v9で実装）

「どのページから勝ちタイム一覧を取るか」が仕様側でも未確定だったため保留されていたが、
**取得元を1つに賭けずに済む作りにして実装した**。勝ちタイムの集め方を3経路用意し、
どれも同じレコード形（`{venue, surface, dist, class, win_time, going?, date?}`）に落として
同じ `build_table()` に渡す。

| `--source` | 中身 | ネットワーク |
|---|---|---|
| `raw`（既定） | コミット済み `raw/*.json` の past_runs から `finish==1` の走を拾う。勝った走の `time_sec` はそのレースの勝ちタイムそのもの | 不要 |
| `file` | 手元のJSON/CSVを読む。`"1:33.4"` 形式のタイムも受ける | 不要 |
| `netkeiba` | レース検索（`?pid=race_search_detail`）を1コース×3年でまとめ取り | 要 |

計算は仕様§4のとおり `median(win_time − class_offset[class] × dist/2000)`。
`--min-samples`（既定5）に満たないコースは表に載せず、未充足コース一覧をレポートに出す。
`COURSES` に JRA10場×芝ダ×距離＝**101コース**を定義してある（§4の「約120通り」に対応）。

### 4.1 ★ netkeibaのDBは pid形式からパス形式に移行していた

ここで**2回URLを外した**。原因は、ネット上の旧いスクレイピング記事が挙げる
`db.netkeiba.com/?pid=race_search_detail` を信じたこと。存在しないpidを投げると、
netkeibaは本文が**赤字でURLを返すだけの応答**をよこす：

```html
<span style="color:red"><b><br>URL: /?pid=race_search_detail<br></b></span>
```

これは v7§2.1 で「実体なし」と結論した `?pid=jockey_leading` と**同じ形**だった。
つまりv7のあの調査も、同じ「pidがもう無い」現象を見ていたことになる。
**この赤字応答を見たらUAやCookieを疑う前にpidを疑うこと。**

DBトップ（`db.netkeiba.com/?rf=navi`）のナビゲーションが正解を持っていた：

| 検索 | 現行URL |
|---|---|
| レース詳細検索 | `https://db.netkeiba.com/race/search_detail.html` |
| 競走馬／騎手／調教師／馬主／生産者 | `…/{horse,jockey,trainer,owner,breeder}/search_detail.html` |

### 4.2 検索クエリの全仕様（実サンプルで確定）

そのフォームの送信先は **`GET https://db.netkeiba.com/race/list.html`**（POSTではない）。

| フィールド | 値 |
|---|---|
| `track[]` | 1=芝 2=ダート 3=障害 |
| `jyo[]` | 01札幌 02函館 03福島 04新潟 05東京 06中山 07中京 08京都 09阪神 10小倉（30以降は地方） |
| `kf` / `kt` | 距離の下限・上限（m）。同値にすればその距離限定 |
| `yf`/`mf`・`yt`/`mt` | 期間の開始・終了（年・月） |
| `baba[]` | 1=良 2=稍重 3=重 4=不良 |
| `class[]` | 1=G1 2=G2 3=G3 4=L 5=OP 6=3勝 7=2勝 8=1勝 9=新馬 10=未勝利 11=未出走 |
| `jyoken[]` | 1=牝馬限定 2=父内国産限定 3=アラブ 4=指定 5=混合 6=特指 7=国際 |
| `barei[]` | 11=2歳 12=3歳 13=4歳 14=4歳以上 |
| `sort` / `limit` | date-desc等 / 20・50・100 |

本スクリプトは `track[]`＋`jyo[]`＋`kf`/`kt`＋期間だけを指定し、**クラスは絞らない**
（§4「全クラスの勝ちタイムを使う」）。クラスは結果のレース名から判定する。

**唯一残る想定値はページ送りの `page`**（フォームのページには現れないため）。
効かなかったときに同じ1ページ目を積み続けないよう、**新規レコードが増えなくなったら打ち切る**
実装にしてある（`tests/test_build_base_times.py` がその挙動を固定）。

結果テーブルのパーサーは列インデックス直指定ではなく**ヘッダー名で列を解決する**ので、
netkeiba側の列構成が変わっても静かにズレない（必要な列が無ければ例外で止まる。
C-6 が指摘している c_horse_history の弱点を、新しいコードには持ち込まない方針）。

### 4.3 現状は表がまだ空

スクリプトは動くが `config/base_times.json` は `{}` のまま（本番で1回も叩いていないため）。
手持ちの raw がまだ無いので `--source raw` でも0件になる。
**表が空である限り①スピード指数は全馬 null**（usable判定#4 で全走が落ちる。
エラーにはならず警告ログが出る）で、②適性と③人的だけが効く状態。
