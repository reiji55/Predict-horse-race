## 2. 今セッションで確定した設計判断（重要な決定のみ）

### 2.1 妙味メーターの未確定2点（引き継ぎ書v2 §3）→ 両方解決

- **信頼度Cに「頭数」を入れるか → 入れない（確定）**。
  理由：運用者の原点仮説は「参加者（賭け金プール）が薄い→歪む」だが、頭数はその弱い代理でしかない。
  そして歪みが本当にあれば妙味の A(最大エッジ)・B(過小評価の広がり) が既に拾うので、頭数をCに足すと二重計上。
  仮説は**式でなく後方検証で検証する**（小頭数レースの回収率をデータで見て、出たら符号付きで項を足す）。
- **`myomi_parts`（旨み度・堅さの内訳）を持たせるか → 持たせる（確定）**。
  umami・conf は妙味計算の途中で既に出る値。将来の2軸メーター化を、貯めた全データで無改修検証できる。

### 2.2 買い目生成（タスク5）の確定事項

- **④オッズ乖離を合成スコアに入れない（最重要）**。入れると妙味が循環する（p がオッズに引かれ、乖離を自分で薄める）。
  → **合成スコア base_score ＝ ①時計②適性③人的 のみ**。④は「妙味メーター」と「買い目選定(value=p−q)」に回す。
  → これが「ケイ⇔源さんの緊張」の正体：ケイは印(①②③)で買い、源さんは妙味(④)で買う。
- 合成方式：**レース内 z 標準化 → 加重和 → softmax**。欠損ファクターは馬ごとに重み再正規化（新馬は①欠損→②③＋不確実フラグ）。
- 初期重み **①0.45 / ②0.30 / ③0.25**（③内訳 騎手0.6/厩舎0.4）。全て config・後方検証でチューニング。
- 印：base_score順に ◎○▲△△✕（△は4〜5位）。印は全キャラ共通、キャラ差は買い目で出す。
- キャラ別 **value寄せ係数 λ**（ケイ0.15/哲0.40/源0.75/鳳0.60）で「堅さ↔妙味」をブレンド。
- 源さんは妙味に振るが **base_score下位すぎる馬は軸にしない**（`axis_base_rank_floor`）＝ただのギャンブルにしない。
- 式別オッズ非取得 → 券種確率は **Harville 式**で単勝pから近似。payout_range は概算。将来 combo_odds に差し替え。
- softmax温度T・myomi_threshold(80) は妙味側 config と共有し二重定義しない。

## 4. タスク6（スクレイパー実装）でやること

共通内部フォーマット仕様 §1・§2 が入力仕様、データスキーマ v1.1 が出力契約。

- **フェッチャー**：netkeiba の6種ページ（A一覧/B出馬表/C馬戦績/D騎手LB/E厩舎LB/Fレース結果）から
  「生の事実だけ」を null 許容で取得 → `raw/{week_id}.json`（共通内部フォーマット §2）に正規化。
- **予想ロジック**：raw → ①②③合成(base_score) → 印 → p変換 → 妙味 → キャラ別買い目 → `predictions.json`。
  仕様は 買い目生成_v1／スピード指数_v1／妙味メーター_v1 のとおり。
- **マナー設計**（共通内部フォーマット §1.1）：リクエスト間隔3秒以上＋ゆらぎ、UA明示、リトライ1回、
  馬戦績ページ(C)は同一週キャッシュ、パース失敗は該当フィールドnullで続行しログ。
- **base_times.json の初期構築スクリプト**（スピード指数 §4）：1回きり。JRA10場×芝ダ×距離の
  勝ちタイム中央値からOP水準へ正規化。どのnetkeibaページを使うかは実装時に確定。
- **作る config**：`config/speed_index.json`（スピード指数§5に雛形）・`config/myomi.json`（妙味§8）・
  `config/cards.json`（買い目§7）・`config/base_times.json`（生成物）。
- **システム構成**：GitHub Actions（workflow_dispatch 手動トリガー）→ Python → JSON生成 → commit → Pages(PWA)が読む。月額0円狙い。

### 5.3 切り替えのアナウンス
- モデル切替・チャット分割の適切なタイミングはアシスタント側から知らせる。

### 5.4 対話スタイル
- 運用者は要望・ニュアンス主体。厳密な仕様は対話で詰める。
- **認識のズレ・データ不足・誤認識は都度指摘**（本人の明示的要望）。噛み砕いて説明、「なんとなく」で進めない。
