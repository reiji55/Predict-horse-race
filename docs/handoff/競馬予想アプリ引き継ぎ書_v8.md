## 2. v8 でやったこと

### 2.1 成果物の統合（リポジトリ化）

チャットごとに散らばっていた添付を1つのリポジトリに集約し、重複を排除した。

- `docs/specs/` 仕様書5点／`docs/handoff/` 引き継ぎ書v1〜v8／`docs/samples/` サンプルJSON／
  `docs/ui/` UIモックとキャラ外見設定
- 捨てた重複：`keiba3cards_skeleton_v4.zip`（`handoff_full.zip` とコード完全一致）、
  引き継ぎ書v2/v4/v6と買い目生成v1の重複コピー、`results.sample` の単体コピー
- 実サンプルHTMLは **netkeibaの著作物なので公開リポジトリには入れない**。
  `.gitignore` を調整し、配置手順の `tests/samples/README.md` だけは残るようにした
  （これまで「サンプルが手元から消える」事故が繰り返された原因がこれ）

### 2.2 仕様書の未反映パッチ（v3 §3・v6 §6 のA群）を全件反映

- データスキーマを **v1.2 として発行**し、`myomi_parts`（`{umami, conf}`）を races[] に追加。
  `predictions.sample.json` にも反映
- 妙味メーター §7 #4・#5 を「要相談」→「確定」に更新（頭数は入れない／myomi_parts は持つ）
- 引き継ぎ書v1 の冒頭に「§5の4ファクター合成はv3 §2.2で上書き済み」の注記を追加
- コードが参照していた **存在しないファイル名**（`データスキーマ仕様_v1_2.md`・
  `妙味メーター仕様_v1_確定版.md`）を実ファイル名に統一

### 2.3 logic の実装（仕様書の検算サンプルをテストに）

`tests/test_logic.py`（26件）は**仕様書の数値をそのまま固定している**ので、
通れば実装が仕様と一致していることになる：

- スピード指数 §1.4 の指数 **82.7**
- 妙味メーター §4 の p/q の表、myomi **73.8**、umami 0.738
- 買い目生成 §6 の sel 値（ケイ A=0.96 / 源さん C=0.875）と **源さんの軸がC（12倍の▲）になること**

券種確率は Harville 近似。`hit_pct` と `payout_range` は**上位3着の順列を全列挙**して
「1点でも当たる確率」と「当たったときの払戻の最小〜最大」を集計している（券種をまたいだ
重複当たりを正しく扱うため）。

### 2.4 build_raw と、土日別実行の週内キャッシュ問題（v5 §3-2 → 解消）

- **絞り込みは A ではなく build_raw の責務**と整理し、`config/scraper.json` で切替可能にした
  （既定＝各場の11R。3場開催の土日で6レース＝取得項目仕様§2.2 の「4〜6」と一致）
- 土日を別々のActions実行で回すと、プロセス内キャッシュでは日曜に同じ馬を取り直してしまう問題は、
  **既にコミット済みの `raw/{week_id}.json` から past_runs を読み直す**方式で解消した。
  日曜ぶんの結果は既存 raw に**マージ**される（上書きしない）

### 2.5 成績集計（タスク7）とUIのデータ接続

- 払戻の4不変条件を計算と検証の両方で実装。
  テストは **`predictions.sample.json` ＋ 公式配当表から `results.sample.json` を再現**する形にした
- UIモックを実データ表示に対応（`docs/ui/adapter.js`）。実データを流したことで見つかった
  UIのバグも修正（GⅠ・GⅡ・1〜3勝クラスが全部「未勝利」バッジになっていた、
  実馬名の長さで印の下の馬名が重なっていた）。Chromium で3画面の描画を確認済み

## 3. ⚠ 実装時に入れた判断（すべて config で切り替え可能）

詳細と根拠は **`docs/OPEN_QUESTIONS.md` B群**に集約してある。特に重要なのは B-1。

| # | 判断 | 効き方 |
|---|---|---|
| **B-1** | `class_credit`（既定 **0.0**） | 仕様§1の式 `expected_time = base_time + class_sec` は、§1が定める「指数100＝OP勝ち馬水準」と矛盾し、**下級条件を遅く走った馬が上級条件を速く走った馬より高い指数になる**（未勝利69.5秒＝96.7 > OP 68.3秒＝91.7）。既定を絶対時計評価にした。`1.0` で仕様書どおりの挙動に戻る |
| B-4 | `amt_unit`（既定 **50**） | 仕様§5.5は100円単位だが、サンプルの哲さんカードに150円がある。サンプルの表現を正とした |
| B-5 | marks は**全出走馬** | 仕様§2の記述どおり（7位以下は `mk: ""`）。後方検証にスコアが要るため。UIは mk が空の行を描画しない |
| B-6 | `score_scale`（既定 **70 + 10×z**） | T=10 は0〜100スケールのスコア前提の値。z のまま割ると妙味が常時振り切れる。妙味§7 #2 が予告していた較正を、Tではなくスコア側で行った |
| B-7 | （様子見） | λが小さいキャラでも、◎が人気を被っていると軸が○に移ることがある。期待値的には妥当だが、ケイの軸を◎固定にしたいなら λ=0 か軸だけ base_rank 順にする改修が要る |

## 5. 進め方のルール（v3から継続・維持）

- **モデル**：実装は Sonnet で十分。設計・仕様整合チェックは Opus
- **対話スタイル**：運用者は要望・ニュアンス主体。認識のズレ・データ不足・誤認識は都度指摘
- **大きい生データ**（HTML等）はチャット直貼りで停止することがあるのでファイル添付を使う
- ギャンブル/ハウスエッジは理解済み。射幸性を煽らず正直な成績表示を重視
- **リクエストマナー**（共通内部フォーマット仕様§1.1）は調査中の試行錯誤でも厳守：
  間隔3秒以上＋ゆらぎ、UA明示、リトライ1回、連打しない
