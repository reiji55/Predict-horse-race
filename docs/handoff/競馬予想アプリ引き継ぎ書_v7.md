## 2. D（騎手リーディング）調査の経過 ★本セッションの成果

### 2.1 試して**ハズレだった**ページ2つ（同じ轍を踏まないこと）

| ページ | 判定 | 理由 |
|---|---|---|
| `db.netkeiba.com/jockey/{jockey_id}/`（例：Ｃ.ルメール, id=05339） | ✕**使わない** | 騎手**個人**の成績ページ。これを騎手の数だけ取るのは、取得項目仕様 §1.2 が「ページ数がかさむ」として明確に却下した**個別ページ方式**そのもの。リーディング一括方式の設計に反する |
| `db.netkeiba.com/jockey/top.html`（騎手TOP） | ✕**使わない** | 実体は「騎手を探す」検索窓のページ。リーディング表は載っていない |

### 2.2 騎手TOPページの解析で分かったこと（技術メモ）

騎手TOPのサイドバーには、リーディング表が入るべき位置に**空のspan**しかない：

```html
<!-- block=get_leading_box (d) -->
<span id="leading_box_area"></span>
<script>
$(function(){
  $.get('https://db.netkeiba.com/leading/ajax_leading_box.html',
        { input:'UTF-8', output:'json' },
        function(data){ if('OK' == data.status){ $('#leading_box_area').html(data.data); } });
});
</script>
```

- **A・B2と同じ「静的HTMLは空、AJAXが後から描画」パターン**がここでも出ている。
  db系ページでも同じ前提で構造解析すること
- ただし `ajax_leading_box.html` は**サイドバー用のミニboxと推測**される（上位数名だけの要約）。
  D が必要とする「場別・全騎手の着度数表」ではない可能性が高い。**本命視しない**が、
  本命ページが取れなかった場合の調査候補として記録しておく（パラメータ不明・未検証）

### 2.3 次に当たるべきURL（**未検証**・Web検索で発見しただけ）

```
本命 : https://db.netkeiba.com/jockey/jockey_leading_jra.html   ← 「JRA騎手リーディング」
別系統: https://db.sp.netkeiba.com/jockey/jockey_leading.html    ← スマホ版「中央騎手リーディング」
旧形式: https://db.netkeiba.com/?pid=jockey_leading
E用   : 上記の trainer 版が同じ規則で存在するはず（未確認）
```

- **いずれも実アクセスによる確認をしていない**。URLが生きているか、中身が静的HTMLか
  AJAXかは次のセッションで確認する必要がある
- **スマホ版（db.sp）は一般にHTMLが軽く素直なことが多い**ので、PC版が重い／AJAXだった場合の
  有力な代替。C（馬戦績）でPC版を使った経緯はあるが、D・Eは表を1枚取るだけなので
  sp版でも要件（着度数の生カウント）を満たせるなら採用してよい

### 2.4 ⚠ 未解決の設計フォーク（**次セッションの冒頭で判断が要る**）

取得項目仕様 §2.6 は騎手を `scope="venue"`（**当該場**の成績）と定めている。
しかし上記リーディングページが**場別の絞り込みに対応しているか未確認**。対応していなかった場合、
以下のどれを取るかの判断が発生する：

| 案 | 内容 | トレードオフ |
|---|---|---|
| ① | 場別フィルタ付きURLを探す（クエリパラメータ等） | 仕様どおり。探索コストが読めない |
| ② | 騎手も `scope="overall"` に落とす（仕様変更） | 1ページで済むが、「小倉の○○は買い」という当該場の妙味が消える。買い目生成仕様 §1.5 の③人的スコアの質が下がる |
| ③ | 詳細検索（`jockey/search_detail.html`）を場条件で叩く | 場別が取れる可能性。ただし検索結果ページの構造解析が別途必要 |

**推奨は ①→③→② の順**。②は仕様の後退なので、①③が両方ダメだった時の最後の手段。
なお②を選ぶ場合、`jockey_stats.scope` の値が変わるので**共通内部フォーマット仕様 §2.6 の改訂が必要**
（黙って値だけ変えないこと）。

### 2.5 実装時の**要確認**ポイント（サンプル入手直後に最初にやる）

リーディング表の騎手リンクが持つ netkeiba ID が、**B出馬表で取得済みの `jockey_ref` と
同じ桁・同じ形式か**を必ず突き合わせる。ここが一致しないと出走馬への振り分けが丸ごと壊れる。
（ルメール個別ページでは `05339` = **5桁ゼロ埋め**だった。B側の実値と照合すること）

## 4. 次にやること（D → E の順を推奨）

D のほうが場別スコープぶん複雑なので、**Dで構造を割ればEはscope替えのほぼ写し**になる。

1. §2.3 のURLに実アクセスし、素のHTMLでリーディング表が埋まっているか確認
2. 空ならDevToolsでAJAXエンドポイントを特定（A・B2で確立した手順）
3. §2.4 の場別フォークを判断
4. 構造解析 → 実装 → 実サンプルで検証（A・B・Cと同じ流れ）
5. `fetch_jockey_leading(venue_jp, period)` → `{jockey_ref: jockey_stats}`
   `fetch_trainer_leading(period)` → `{trainer_ref: trainer_stats}`
   いずれも**着度数の生カウント**で返す（率の計算はロジック側＝共通内部フォーマット §2.0 原則1）
