## 2. A（レース一覧）で確定した実装内容と技術的発見

実サンプル：2026年6月20日(土)、東京・阪神・函館の3場・計36レース（うち代表的なもので検証）。

### 2.1 B・B2と同じ「JS/AJAX描画」パターン

`race_list.html?kaisai_date=YYYYMMDD` を素で取得しても中身は空。**2段階のAJAX**が必要：

1. `GET race_list_get_date_list.html?kaisai_date={YYYYMMDD}&encoding=UTF-8`
   → 日付タブ一覧のHTML断片。目的の日付の `<li date="{YYYYMMDD}">` が持つ `group` 属性値が、
   次のステップで使う `current_group` パラメータそのもの
2. `GET race_list_sub.html?kaisai_date={YYYYMMDD}&current_group={group}`
   → 実際のレース一覧本体（場ごとに1〜12R程度）

`group` の値の意味（"10"+その週の土曜日付、のように見える）は未確認のため決め打ちせず、
**必ずステップ1のレスポンスから実際の値を読む**設計にした（ステップ1・2で計2リクエスト/日、
週合計4リクエスト。ページ数見積もりへの影響は軽微）。

### 2.2 パースできる項目・できない項目

| 項目 | 状況 |
|---|---|
| race_id・R番号・レース名・発走時刻・距離/馬場・頭数 | ◎パース済み・検証済み |
| グレード（条件戦：未勝利/1勝クラス等） | ◎`constants.CONDITION_GRADE_MAP` で判定可（Cと共有） |
| グレード（特別戦・重賞の固有名） | ▲**未確定**。Aページのグレードアイコン番号（5,16,17,18等）は、
  Bページで確認済みの `Icon_GradeType{1,2,3}`→g1/g2/g3 とは別スケールで、対応関係を確認できていない。
  誤った決め打ちを避け、`grade=None` + 生アイコンクラスを `grade_icon_raw` に温存する設計にした。
  **【要確認】**後日Bページの結果と突き合わせて確定させる |
| ハンデ戦フラグ（course.note） | ▲**推定判定**。RaceData内の `Icon_GradeType13` の有無で判定しているが、
  実際のレース条件との照合による推定（6件中5件が一致するパターンから判断）。**【要確認】** |
| 天候 | ✕**未取得**。アイコン専用でテキストが無く、アイコン番号→天候名の対応が未確認のため見送り。
  B出馬表側がテキストで取得済み（v4§2.2）なのでそちらを正とする |

## 4. 次にやること：D・E（リーディング）

取得項目仕様 §1.1（表D・E行）・§2.6（stats型）が仕様。v5から引き続き未着手。

- **D 騎手リーディング（場別）**：`fetch_jockey_leading(venue_jp, period)` → `{jockey_ref: jockey_stats}`。
  jockey_stats は §2.6（scope="venue", venue, period, starts, wins, seconds, thirds）。着度数の生カウントで保持。
- **E 調教師リーディング**：`fetch_trainer_leading(period)` → `{trainer_ref: trainer_stats}`（scope="overall"）。
- 紐付けキー：出走馬の jockey_ref / trainer_ref（B出馬表で取得済み）とリーディング表を突合。

いずれもこれまでと同じ流れ（**HTMLサンプル入手 → 構造解析 → 実装 → 実サンプルで検証**）。
D・EはA・B・Cと違い、条件面での確認事項（絞り込みルール等）は無い想定。純粋に技術的な
構造解析のみで進められる見込み。

**HTMLサンプル入手方法**：D・Eはリーディングページなので、netkeiba上の該当ページ
（騎手リーディングは場別、調教師リーディングは全体）のURLをブラウザで開いてHTMLソースを保存 →
このチャットに添付、の流れで進める。JS/AJAX描画の可能性もあるため、まずは素のHTML取得を試し、
中身が空ならA・B・B2と同じ「AJAX直叩き」調査に切り替える。
