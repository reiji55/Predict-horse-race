## 2. Priority 2 — character score → p → EV consistency

### Previous inconsistency

Claude's 2026-09-19 redesign correctly introduced character-specific `score_weights`, but those weights only changed the **ability ranking**.

For example:

- Gen used an aptitude-heavy ability ranking.
- However, Gen's EV was still calculated with the common/global `h["p"]`.
- That common p came from the shared 45/30/25 score model.

So the implementation effectively said:

> "Gen believes aptitude should matter 55% when ranking ability, but when computing EV he uses a probability generated by somebody else's 45/30/25 model."

That makes character-vs-character experiments difficult to interpret.

### Changes

#### `logic/cards.py::assign_character_ranks`

When a character has `score_weights` and raw factors are available:

1. Recompute the character-specific composite z score using `base_score.composite_scores`.
2. Convert that score with `base_score.to_display_score`.
3. Run `prob_model.softmax_scores(..., temperature)`.
4. Store the resulting character-specific probability as `sel_p`.
5. Calculate the character's objective (`p-q` or `p*odds-1`) using that **same `sel_p`**.
6. Rank ability and value from the same character model.

Temporary per-horse fields used during card creation:

- `sel_base_rank`
- `sel_score`
- `sel_p`
- `sel_value`
- `sel_value_rank`

If EV cannot be computed because win odds are unavailable, fallback to `p-q` now preserves the character-specific p rather than reverting to the common p.

#### `logic/cards.py::generate_card_for_character`

New optional parameters:

- `temperature`
- `combo_odds`

Card `hit_pct` / Harville probability calculations now use the character's `sel_p`, not the common `h["p"]`.

Each card now records:

```json
"probability_model": {
  "temperature": ...,
  "score_weights": ...
}
```

This is intended to make future audit/replay easier.

### Important caveat

This fixes **internal consistency**, not statistical calibration.

The probabilities are still produced by softmax from a hand-designed score. They have **not yet been calibrated against historical outcomes** with Brier score, log loss, calibration curves, isotonic/Platt/etc.

Therefore:

- "p" is structurally consistent with each character,
- but it must **not yet be assumed to be an empirically calibrated win probability**.

Probability calibration remains the next major modeling task.

### Test coverage

`tests/test_priority_1_3.py::test_character_weights_recompute_probability_not_only_rank`

`tests/test_character_objectives.py` was updated so EV→PQ fallback expects the character-specific p to remain in force.

## 3. Priority 3 — Otori activation from the exact card's market EV

### Previous inconsistency

Previously the race-level myomi meter could be raised by a high single-horse win EV:

`max(p_i * win_odds_i)`

but Otori selected a different set of horses using a blended ranking.

That allowed the logically inconsistent state:

> A horse makes myomi exceed 80 → Otori appears → Otori does not buy that horse at all.

Also, actual Wide/Quinella/Trio market odds were not being used for the bets that the app recommended.

### 3A. Fetch actual combination odds

#### `scraper/fetchers/b2_odds.py`

The existing constants already knew:

- type=4 → 馬連
- type=5 → ワイド
- type=7 → 3連複

The fetcher now retrieves those types separately in addition to type=1.

Why separate calls?

- The first live run already established that `type=all` could return an empty response.
- Therefore each ticket type is requested independently.

New normalized raw representation:

```json
"combo_odds": {
  "馬連": {
    "2-9": 269.9
  },
  "ワイド": {
    "2-9": [45.2, 66.9]
  },
  "3連複": {
    "2-9-10": 2252.8
  }
}
```

Combination keys are sorted horse numbers joined with `-`.

For Wide, the market supplies a range; downstream EV uses the **lower bound** to avoid optimistic overstatement.

If one combination-odds fetch fails, win odds still survive and the pipeline continues. The missing ticket type is treated as missing market-EV evidence.

#### `scraper/build_raw.py`

Documentation/comments now explicitly describe collection of Wide/Quinella/Trio market odds.

### 3B. Evaluate the exact card

#### `logic/cards.py`

Added:

- `market_odds_for_bet`
- `evaluate_market_card`

For each bet:

```text
expected_payout = P(hit) * market_odds * stake
```

For the whole card:

```text
expected_roi = sum(expected_payout) / total_stake
edge = expected_roi - 1
```

Important conservative rule:

- If **any point in the card lacks an actual market odd**, `complete=false`.
- An incomplete card is **not** allowed to trigger Otori.
- This avoids cherry-picking only the bets for which favorable odds happened to be available.

Each generated card now includes `market_ev` with:

- completeness / coverage
- per-bet model probability
- actual market odds used
- expected payout
- expected ROI
- edge

### 3C. Myomi / Otori gating

#### `logic/myomi.py`

Added `compute_card_ev_myomi`.

For an Otori candidate card:

```text
edge = max(expected_roi - 1, 0)
umami = min(edge / card_edge_cap, 1)
myomi = 100 * umami * confidence
legendary = myomi > threshold
```

Current config:

```json
"card_ev": {
  "edge_cap": 0.5,
  "require_complete": true
}
```

This means +50% expected card edge saturates the EV component.

If actual combination odds are unavailable/incomplete:

- myomi = 0
- legendary = false
- `myomi_source = "otori_market_card_ev_unavailable"`

This is intentionally conservative.

#### `logic/build_predictions.py`

New order of operations:

1. Build common factors/marks/p/q as before.
2. Preserve the **old model-vs-market disagreement myomi** as a diagnostic:
   `model_disagreement_myomi`.
3. Generate an Otori candidate **even before activation**.
4. Evaluate that exact candidate against actual combination market odds.
5. Compute the user-facing myomi from that card EV.
6. Add Otori to `cards[]` only if that card-EV myomi exceeds the threshold.
7. Generate the regular three cards.

New race-level fields:

- `myomi_source`
- `otori_card_ev`
- `model_disagreement_myomi`

The old disagreement signal was not deleted; it is retained for analysis, but it no longer decides Otori activation.

#### `logic/snapshots.py`

The new EV/myomi provenance fields are frozen with the pre-race snapshot so later result analysis can see what caused activation at prediction time.

### Test coverage

- Wide lower-bound usage
- actual market-card EV

- Otori card-EV myomi activation/deactivation

## 5. What this branch intentionally did NOT change

Do not interpret this branch as "the betting model is solved."

Still open:

1. **Probability calibration**
   - softmax p is not empirically calibrated.
   - This is the biggest remaining mathematical caveat for EV calculations.

2. **Walk-forward / historical backtest**
   - need genuine out-of-sample evaluation.
   - 2026-09-19 must not be reused as evidence for the weights that were designed after seeing its result.

3. **CLV / odds history**
   - final pre-race snapshot exists, but full time-series odds history is not yet stored.

4. **Human score data quality**
   - `thirds` can be missing; the current "place rate" can effectively behave like a quinella/連対 rate.
   - missing jockey/trainer coverage remains an issue.

5. **Confidence semantics**
   - still dominated by usable speed-run coverage and should not be read as calibrated model certainty.

6. **Race-condition parsing**
   - the prior review found cases such as race `note="ハンデ"` inconsistent with the actual condition.
   - not fixed in this branch.

7. **Results provenance**
   - prediction cards now carry `objective`, `probability_model`, and `market_ev`.
   - `results/build_results.py::settle_card` still does not preserve all of those fields in result cards.
   - Consider fixing this before long-term model comparisons.

8. **Model/config version hash**
   - there is not yet a stable model version/config hash attached to each frozen prediction.

9. **Fresh live validation of combo odds**
   - parsing is covered by synthetic fixtures/tests.
   - the type=4/5/7 shape is based on the netkeiba odds API structure already documented in this repo.
   - It should still be verified on the next real pre-race network run before trusting production Otori activation.
