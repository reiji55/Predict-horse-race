# Phase 1 過去データ取得 仕様 v0（ドラフト）

- 作成: 2026-10-24 / Claude
- 監査予定: ChatGPT
- 前提: `RESEARCH_DESIGN_v0.md` §7 のオーナー判断（取得元＝netkeiba、取得したデータはリポジトリにコミット、対象＝JRA平地競走全体、判断時刻＝発走30〜60分前、置き場所＝`lab/`）

---

## 1. 方針

1. **取得は GitHub Actions で行う。** Claude のクラウド環境からは netkeiba に接続できない（ネットワーク設定で遮断）。本番パイプラインは Actions から取得できているので、lab の取得も Actions の専用 workflow で行い、結果をコミットする。コミット時刻が「いつ取得したか」の証拠にもなる。
2. **既存のマナーを守る。** `scraper/common/http.py` と同じく、リクエスト間隔3秒以上＋ゆらぎ、User-Agent を偽らない、リトライ1回。**並列実行はしない**（取得を急ぐために同時に複数ジョブを走らせない）。
3. **コミットするのは取り出した事実（JSON/CSV）だけ。** ページの HTML そのものはコミットしない（既存リポジトリの方針と同じ）。
4. **馬ごとの戦績ページは取得しない。** 全レースの結果を集めれば、各馬の過去走はそこから組み立てられる。そのほうが「発走時点で分かっていた過去走だけ」を正確に再現でき、リクエスト数も少ない。
5. **本番のスクレイパー（`scraper/`）は変更しない。** 解析方法は既存の実装（実サンプルで確かめ済み）を参考にするが、lab 側に独立したコードとして書く。

## 2. 取得するページ

| # | ページ | URL | 取れるもの | 回数の目安 |
|---|---|---|---|---|
| L1 | 開催日のレース一覧 | `race.netkeiba.com/top/race_list_get_date_list.html` → `race_list_sub.html`（既存 `a_race_list.py` と同じ2段階） | その日の全レースの race_id・場・R・発走時刻・レース名 | 開催日あたり2回（年間約290回） |
| L2 | レース結果 | `race.netkeiba.com/race/result.html?race_id=…`（既存 `f_results.py` と同じページ） | 着順・枠・馬番・馬名と馬ID・性齢・斤量・騎手とID・タイム・着差・人気・単勝オッズ（確定）・上がり3F・コーナー通過順・厩舎・馬体重（増減）、払戻の全券種、レース条件 | 1レース1回（年間約3,450回） |
| L3 | 確定オッズ（任意・第2段階） | `race.netkeiba.com/api/api_get_jra_odds.html`（既存 `b2_odds.py` と同じAPI） | 複勝の幅・馬連・ワイド・3連複の確定オッズ | 1レース4回程度 |

- L3 は**過去のレースでも確定オッズが返るかを、まず数レースで確かめてから**決める。返るなら、組合せ馬券（ワイド・3連複など）の期待値を過去データでも検証できる。返らなければ、組合せ馬券の検証は Phase 6 の前向き検証だけで行う。
- L1・L2 のページ構造（列の並び・ラップタイムの有無など）は、過去の年でも同じかを最初の疎通確認で確かめる。古い年は列が違う可能性がある。

## 3. 期間と量

| 区間 | 期間（案） | 用途 |
|---|---|---|
| 助走 | 2019年 | 2020年以降のレースの「過去走」を作るためだけに使う。モデルの評価には使わない |
| 開発（Dev） | 2020-01〜2023-12 | 特徴量・モデルの開発 |
| 検証（Val） | 2024-01〜2024-12 | モデルの選択 |
| 封印ホールドアウト | 2025-01〜2026-09 | 事前登録した最終候補を1回だけ評価 |
| 前向き検証（Live） | 2026-10以降 | 発走前に予測をコミットして採点 |

- 2019〜2026-09 で約26,000レース。L1＋L2 で約28,000リクエスト、1リクエスト平均4.5秒で**約35時間**。Actions の1ジョブは最大6時間なので、**1か月分ずつ、順番に約8〜10回に分けて**取得する（同時には走らせない）。
- データ量は1年あたり出走約4.8万行。月ごとの圧縮 JSON で、全期間合わせて数十MB程度の見込み（GitHub の1ファイル100MB制限に十分収まる）。
- 区間の境界は、ChatGPT の監査を経て v1 で確定する。必要ならあとから2015年まで遡って助走・開発を延ばす。

## 4. 保存形式

```
lab/data/
├── raw/netkeiba/
│   ├── race_list/{YYYY}/{YYYYMMDD}.json        L1 の解析結果
│   └── results/{YYYY}/{YYYYMM}.jsonl.gz        L2 の解析結果（1行1レース）
├── manifests/{YYYYMM}.json                     取得した race_id の一覧・件数・失敗・SHA-256・取得時刻・コードの git commit
└── db/                                          raw から作る分析用テーブル（再生成可能）
```

1レースの記録（L2）には次を必ず含める。

- `race_id`、`fetched_at`（取得した時刻）、`parser_version`
- レース条件: 日付・場・R・発走時刻・芝ダ・距離・馬場・天候・クラス・頭数・ハンデ等の条件
- 出走馬ごと: 上の L2 の列すべて＋取消・除外・中止の区別
- 払戻: 全券種

## 5. 各項目の「いつ分かるか」（`available_at`）

研究で特徴量に使えるのは、判断時刻（発走30分前）より前に分かる情報だけ。

| 項目 | いつ分かるか | 同じレースの予測に使えるか |
|---|---|---|
| 枠・馬番・馬名・性齢・斤量・騎手・厩舎・レース条件 | 前日の出馬表確定時 | 使える（乗り替わりは当日の発表時刻） |
| 馬体重・増減 | 発走の約60〜70分前 | 判断時刻（30分前）なら使える |
| 馬場状態・天候 | 当日（変わることがある） | 判断時刻の値なら使える。結果ページの値は最終値なので「近似」と明記する |
| 着順・タイム・着差・上がり・通過順・払戻 | 発走後 | **使えない**（過去走としてのみ使う） |
| 単勝オッズ・人気（結果ページ） | **確定時（発走後）** | 判断時刻のオッズではない。過去データでは「確定オッズ」として区別して扱う（§6） |

過去走として使う場合は `run.date < race.date` で切る（同じ日のより早いレースは v1 では使わない）。

## 6. 判断時刻とオッズ

- **判断時刻は発走30分前を主とし、60分前も記録する。** GitHub Actions の定期実行は数分〜十数分遅れることがあるので、30〜60分前という幅は運用上も都合がよい。
- **過去データには判断時刻のオッズがない**（netkeiba の過去ページで分かるのは確定オッズ）。そこで:
  - RQ1（確率の正確さ）の過去データでの比較は、**確定オッズの市場確率**を相手にする。確定オッズは直前の情報まで反映しているので、30分前のオッズより手強い相手になる（保守的な比較）。
  - 市場確率をモデルの入力に使う統合モデル（Phase 4）を確定オッズで学習・評価すると、実際には使えない情報を使った**楽観的な結果**になる。過去データでの結果は「上限」として扱い、本当の評価は Phase 6 の前向き検証で、30分前のオッズを使って行う。
- **Phase 6 に向けて、早めに全JRAレースの前向きオッズ記録を始める**（別の小さな workflow）。発走60分前と30分前に、単勝・複勝（可能なら馬連・ワイド・3連複も）を記録し、確定オッズとの差を測る。1日あたり約36レース × 2時点 × 1〜4回 ＝ 最大約300リクエスト。

## 7. データ品質の確認

- 年ごとのレース数・開催日数・出走頭数を、JRA の公表値と照合する。
- 1レース内で: 着順の重複・欠番、馬番の重複、確定オッズの逆数の合計（控除率と整合するか、約1.25前後）、払戻と着順の整合（単勝の払戻＝1着馬の単勝オッズ×100 になっているか）。
- 取得の失敗は消さずに manifest に理由を残し、推測で埋めない。
- 品質レポート（`lab/docs/reports/data_quality_*.md`）と照合用の集計値を出し、ChatGPT が独立に照合する。

## 8. 最初の一歩（疎通確認）

本格取得の前に、Actions で小さな確認を1回だけ行う。

1. 2019・2022・2025年から開催日を1日ずつ選び、L1 と L2 を取得して解析できるか（古い年で列が違わないか）。
2. 過去のレース3つで L3 が確定オッズを返すか。
3. 取得結果・解析結果の件数を出力し、本格取得の前に Claude と ChatGPT で確認する。
